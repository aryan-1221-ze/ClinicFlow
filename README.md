# ClinicFlow

A healthcare **administration and practice-intelligence prototype**: appointment-request tracking, a searchable doctor directory with CSV import, and an AI-assisted drafting workspace for routine administrative messages.

> **Independent prototype.** Built for an AI Skills and Prompt Engineering assessment. It is not a product of any healthcare provider. All bundled data is fictional. Nothing is booked with a real clinic, and no message is ever sent automatically.

## Features

- **Overview**: database-backed counts (total, pending, confirmed, cancelled, doctors), upcoming requests, recent activity.
- **Appointments**: create, view, edit, change status, cancel or delete (both behind a confirmation page), search and filter by text, status and date range, pagination.
- **Doctor Directory**: CSV upload with header normalisation, field validation, missing-value reporting, duplicate detection (file and database), search, specialty and city filters.
- **AI Assistant**: categorise an enquiry, draft a reply from operator-supplied facts, draft a confirmation or reminder for a confirmed appointment. Output is editable and copyable.
- **Activity Log**: appointment changes, CSV imports, AI requests (logged without the text entered).
- **Settings**: clinic display name and a read-only status of the AI and upload configuration.

## Technology stack

Python 3 · Flask · Jinja2 · SQLite (`sqlite3` standard library) · vanilla JavaScript · plain CSS · pytest. The LLM call uses `urllib` from the standard library, so there is no SDK dependency.

## Architecture overview

```
Browser --> routes.py (one blueprint) --> models/*  (SQL, validation) --> SQLite
                  |
                  +--> services/csv_import.py   (pure parse/validate, then insert)
                  +--> services/ai_service.py   (LLM call + deterministic fallback)
                  +--> services/security.py     (CSRF, security headers)
```

See `docs/architecture.md` for the request flow and the decisions worth understanding before you present this.

## Prerequisites

- Python 3.10 or newer (developed and tested on 3.12)
- `pip`

## Setup

```bash
cd clinicflow
python -m venv .venv
source .venv/bin/activate          # Windows: .venv\Scripts\activate
pip install -r requirements.txt
cp .env.example .env               # Windows: copy .env.example .env
```

Edit `.env` and set `SECRET_KEY` (generate with `python -c "import secrets; print(secrets.token_hex(32))"`). Without it a temporary key is used and sessions reset on every restart.

## Database initialisation

The app creates its tables automatically on start. With `AUTO_SEED=1` (the default) it also loads fictional demo appointments and the 12 sample doctors **once**, into an empty database. To do it explicitly:

```bash
flask --app app init-db --seed
```

The database file is `database/clinicflow.db` (git-ignored). Delete it to start fresh.

## Run

```bash
python app.py
```

Open http://127.0.0.1:5000. The app binds to localhost and runs with debug off.

## Tests

```bash
python -m pytest -q
```

The tests use a temporary database per test and need no network or API key. The live-AI code path is tested with a mocked transport; see Known limitations.

## CSV import

Open **Doctor Directory**, choose a `.csv` file and select *Validate and import*.

| Column | Required | Notes |
|---|---|---|
| `name`, `specialty`, `practice`, `city` | yes | |
| `phone` | no | digits, spaces, `+ ( ) . -`, at least 6 digits |
| `email` | no | basic format check |
| `source` | no | URL or description; shown as a link only if it starts with http(s) |
| `last_verified` | no | `YYYY-MM-DD`, not in the future |

Common alternative headers (for example `Doctor Name`, `Clinic`, `Region`, `Source URL`) are recognised. Unknown columns are ignored and listed. Invalid rows are skipped and reported by line number; values are never altered or invented. Duplicates are matched on name plus practice, ignoring case and extra spaces. Limits: `.csv` only, UTF-8, 1 MB and 5000 rows by default (`MAX_UPLOAD_BYTES`, `MAX_CSV_ROWS`). Uploads are processed in memory and not stored.

Try `sample_data/doctors_sample.csv` (clean, fictional) and `sample_data/doctors_sample_with_errors.csv` (shows each kind of problem report).

## AI configuration and fallback

1. Set **one** of `ANTHROPIC_API_KEY` or `OPENAI_API_KEY` in `.env` (never commit it). Optional: `AI_PROVIDER` (`anthropic`, `openai` or `none`), `ANTHROPIC_MODEL`, `OPENAI_MODEL`.
2. Restart the app. The AI Assistant page shows "Live AI on" with the provider and model.

Without a key, or if the service fails or returns unusable output, the assistant returns a **deterministic template** labelled "Fallback template - NOT generated by an AI model", with a message saying why. Safeguards:

- Possible medical enquiries (symptoms, medicines, doses and similar keywords) are never sent to an AI service and are routed to *Human assistance required*.
- Emails and phone-like numbers are replaced with placeholders before any external call. Clinic contact details typed under "Facts" are restored locally in the draft.
- Patient names and appointment notes are never sent. The appointment message uses a `{patient_name}` placeholder that is filled in locally.
- Keys are read from the environment at call time, never logged, rendered or returned.
- Nothing is sent to patients. Every draft is for human review.

## Security measures

CSRF tokens on every state-changing request (forms and JSON), parameterised SQL, Jinja auto-escaping, a strict Content-Security-Policy (no inline scripts or styles), file type/size/row limits, no tracebacks shown to users, HttpOnly and SameSite session cookies (`SESSION_COOKIE_SECURE=1` behind HTTPS). There is deliberately **no login**; see below.

## Known limitations

- **No authentication or roles.** Anyone who can reach the server can use it. Run it on localhost only. Do not deploy as-is.
- **Not real patient software.** Free-text fields cannot be proven free of sensitive data; the UI warns and the AI path redacts contact details, but there is no general PII detector.
- Redaction is pattern-based (emails, phone-like numbers). Names and addresses typed into an enquiry are not detected.
- **The live LLM path has not been exercised against a real provider** in development. It is covered by mocked tests only. Try it with your own key and record the result in your prompt log.
- The AI endpoints have no rate limiting. Times are stored and shown in UTC.
- Clinical keyword screening is a coarse safety net, not a classifier. It can over-flag.
- No email/SMS integration, by design.
- Visual layout and responsiveness have not been checked in a real browser during development (see manual checks in `docs/architecture.md`).

## Deployment considerations

Do not use `python app.py` in production. Add authentication and authorisation first, use a production WSGI server (gunicorn or waitress) behind HTTPS, set a persistent `SECRET_KEY` and `SESSION_COOKIE_SECURE=1`, move from SQLite to a managed database if more than one worker or host is needed, add rate limiting on `/assistant/*`, and review privacy and regulatory obligations (for example HIPAA or GDPR) before handling any real data.
